🌐 Public API Endpoints

These endpoints are publicly accessible without authentication. All responses include a _meta field with endpoint descriptions and field documentation.

🟢 GET /api/health No rate limit

Purpose: Server health check and status verification. Returns server timestamp and operational status.

Response Fields:
• ok: Boolean indicating server is operational
• time: Current Unix timestamp (seconds since epoch)
• outputs_dir: Absolute path to model outputs directory
• _meta: Endpoint metadata with field descriptions
🟢 GET /api/capacity No rate limit

Purpose: Real-time platform capacity and usage statistics across all subscription tiers. Shows user counts, available slots, worker status, and processing queue.

Response Structure:
• capacity.{tier}.current: Number of registered users
• capacity.{tier}.max: Maximum allowed users
• capacity.{tier}.available: Remaining slots
• capacity.{tier}.percent_full: Usage percentage
• capacity.workers.active: Active worker processes (1-20)
• capacity.workers.processing: Models currently generating
• capacity.workers.queue_length: Pending tasks
• capacity.workers.total_processed: Total models since server start
🟣 POST /api/check-username 30/min

Purpose: Check if a username is available for registration. Used for real-time validation during signup.

Request Body: {"username": "string"}
Response: {"available": boolean, "message": "string"}
Validation Rules: 3-20 chars, alphanumeric + underscore, must start with letter, case-insensitive
📝 Example Usage
// Fetch platform capacity
fetch('http://localhost:5000/api/capacity')
  .then(res => res.json())
  .then(data => {
    console.log('Metadata:', data._meta);
    console.log('Free tier:', data.capacity.free);
    console.log('Workers:', data.capacity.workers);
  });

🔥 Rate Limit Overview

SlushAI implements a fair-use rate limiting system to prevent abuse while ensuring reliable service for all users. Limits are applied per IP address and per user account.

🛡️ Progressive Security Blocking

Our multi-tier blocking system automatically detects and prevents abuse with increasing severity:

Level 1: Rate Limit Warning
429 error returned, retry after cooldown period (1-60 seconds)
Level 2: Temporary Block
1-hour block for excessive requests (>100 req/min sustained)
Level 3: Extended Block
24-hour block for attack patterns (SQL injection, XSS, path traversal)
Level 4: Permanent Ban
DDoS attacks (>1,000 req/10s), repeated malicious activity
🔍 Real-Time Attack Detection
Our security system automatically detects and blocks:
• SQL Injection: Pattern matching for UNION, SELECT, DROP, etc.
• XSS Attempts: Script tags, javascript: URIs, event handlers
• Path Traversal: ../ sequences, /etc/ access attempts
• Command Injection: Shell metacharacters, eval patterns
• DDoS Attacks: Sustained >1000 req/10s threshold
• Brute Force: Repeated failed login attempts
📊 All attacks are logged for 3 months in separate error logs for troubleshooting and security audits.
✅ Best Practices to Avoid Blocks
1. Implement exponential backoff when receiving 429 errors
2. Cache API responses where appropriate (capacity data, etc.)
3. Use proper authentication instead of relying on IP limits
4. Respect rate limit headers in API responses
5. Batch requests when possible instead of rapid-fire calls
6. Handle errors gracefully and don't retry indefinitely
7. Monitor your quota usage via the Account tab
